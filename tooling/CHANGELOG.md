# Changelog of `Luna-Flow/floating-tools`

The developer tools of [`Luna-Flow/floating`](../library/README.md): benchmarks,
command-line programs, the corpus frontends, the differential harness and the
documentation examples. The module has the version of the library and imports the
library of that version; the changelog of the library is
[`library/CHANGELOG.md`](../library/CHANGELOG.md). An entry that changes only this
module goes here (see `CONTRIBUTING.md`, "Release Checklist").

## Unreleased

- Names changed in 0.12 ([#438](https://github.com/Luna-Flow/floating/issues/438)): the packages, tools and data that carried the name of the interval type or of `bin_float` follow the renames of the library to `Interval` and `Binary`. One row per item that existed in 0.11.0, sorted by area; the tools and outputs that are new in this release (`tools/interval_diff.py` and its files, `differential/interval_mpfr`, the output tokens `INTERVALDIFF_*` and the row format `interval-diff-v1`, `tools/kernel_units.py`, `tools/verify_mutation.py`) are written with the final names in the entries that introduce them. Not a behaviour change.

- The decTest stage can record deviations of the corpus (`testdata/decimal_gda/deviations.tsv`, `--deviations`): a row whose token is a value other than the one the library returns, both inside the tolerance of the specification, is judged against the held value, reported as the verdict `deviation`, and fails if its token stops being the recorded corpus value ([#438](https://github.com/Luna-Flow/floating/issues/438), [#649](https://github.com/Luna-Flow/floating/issues/649)).
- Exponent fields that tell a wrapping reader from a saturating one ([#624](https://github.com/Luna-Flow/floating/issues/624)): `tools/exponent_field_rows.py` (a generator of rows per radix, the format's rule as a parameter: `exponent_field_rows(radix, rule)`; `BinaryRule` is the rule of a binary format, written in Python from IEEE 754-2019 7.4 and 7.5 with exact `Fraction` arithmetic) and `tools/generate_exponent_field_rows.py` write `exponent_field_rows_wbtest.mbt` (1,456 rows, 208 of them the first literals above the largest finite number: 2^(e_max + 1), the midpoint above it and their neighbours in hexadecimal and decimal, all four directions, for the context readers and for `from_string` and `from_hex`). Fields 2^63 - 1, 2^63, 2^63 + 1, 10^19, 2^64 - 1, 2^64, 2^64 + 1 and a 40-digit one, each for both signs of the exponent, significands 1 and 0 (signed zero whatever the exponent), both signs of the number, decimal and hexadecimal text, binary64 and the default context, plus long-fraction rows that come back into range. `from_string_ctx`, `from_hex_ctx`, `from_string` and `from_hex` are all tested; the old decimal reader fails the first of these rows (`1e+9223372036854775808` read as 0).
- Exponent fields of 10 digits and more are in the oracles of the two readers (issues [#597](https://github.com/Luna-Flow/floating/issues/597) and [#624](https://github.com/Luna-Flow/floating/issues/624)). `tools/generate_hex_ctx_rows.py` adds 1,300 rows to `hex_ctx_rows_wbtest.mbt` (5,095 in all, 3,795 before): fields of 10 to 41 digits (2^31 to 10^40, both signs, the 2^32, 2^63, 2^64 neighbours) over, under and at the edges of every format, fields of 20 to 40 digits with leading zeros whose value is small, and the edge of the implementation range with the point moving the value back. The MPFR `strtofr` corpus grows from 1,434 to 3,699 rows (`tools/generate_mpfr_decimal_string_oracle.c`, the first 1,434 rows unchanged): fields of 10 to 41 digits in the directions the result is well defined, and long zero-padded fields. Both new blocks fail on the library before the fixes (288 of 3,699 `strtofr` rows before 03e88483; the hex test before 6e60ce96) and pass now.
- External baseline, the validation is stated and made independent of the library's readers (x-js's oracle audit of 2026-11-21, items 2.3.9 and 5.7). (a) A run without a reference result no longer prints `EXTBENCH_FAILED=0`: the benchmark prints `EXTBENCH_NOT_VALIDATED=<cases>` for the cases without one (and `EXTBENCH_FAILED=<n>` only when every case was compared), each `EXTBENCH_CASE` line says `validated=yes|no`, `operands=` and `distinct=`; `external_baseline.py` records the state per round (`validated`, `failed`, `not_validated`, or `unknown` for a log without a verdict line, never `validated`), warns for anything but `validated`, prints "NOT VALIDATED" under the table of `quick` (which passes no reference) and writes `validation` into the summary and a validation paragraph on the page. (b) The reference results of MPFR (`%Ra`) and libmpdec (`mpd_to_sci`) and the text the library prints are compared as canonical text produced by one small parser in `bench/external/canonical_test.mbt` (binary: sign, odd integer significand in binary and exponent, `0`/`-0`, `inf`, `nan`; decimal: sign, coefficient with its trailing zeros, exponent), not through `Binary::from_hex`/`to_number` and `compare == 0`: the sign of zero, the decimal cohort, infinities and NaN are compared; the parser is tested with expected texts written out (including the formats MPFR prints), and the comparators with the sign of zero, the cohort and a wrong value. A corrupted reference file makes the run report `EXTBENCH_FAILED=2` (checked). (c) The summary reports the number of distinct operand sets per case (`validation.distinct_operands_per_case`; 8 operands repeated in every round and block are one check, not many) and the page says so. (d) The benchmark specs of `bench/binary`, `bench/interval`, `bench/decimal` and `bench/decimal_gda` whose reference is the code under test or its sibling are labelled in the code as timing harness checks with no validation claim (levels S, C, or A for core `BigInt`); the `null` and `floating` implementations of `bench/external` are timing paths.
- The differential stage of `interval` is the last stage of `just gate interval` (`INTERVAL: interval against the oracles`). The oracle in Python integers decides every arithmetic row with nothing but CPython and is the required one (it now covers the 78 rows it skipped, which were far addends more than 4,000 bits below the other term and rows MPFR's `mpfr_sqrt` could not decide: a far addend only decides the side of the rounding, so the sum is the larger term scaled to p + 2 bits plus a remainder; 1,584 of 1,584 arithmetic rows, agreeing with MPFR on all); MPFR decides all rows, `exp` and `ln` included, when its headers are found, and the report prints which oracles ran with their row counts, the rows not checked without MPFR, and the rows each oracle decided; `--no-mpfr` and `--require-mpfr` select the modes; the exit status is 1 for a new difference, a stale known row, a class that missed its band or two oracles that disagree. For `exp` and `ln` the report gives the excess over the tightest bound in units of the last place per class, operation and precision (all 408 rows have excess 0 today: valid is accurate there). A mutation of the integer oracle's rounding direction fails 1,170 rows.
- The differential stage of `interval` against MPFR covers `exp` and `ln` ([#569](https://github.com/Luna-Flow/floating/issues/569) regression rows): classes `XOV` (arguments next to `(e_max + 1) ln 2`, 117 to 292 bits as well), `XUF` (next to `e_min ln 2`, the smallest subnormal and its half) and `LNE` (the ends of the range and next to 1), and `exp`/`ln` in the ordinary, few-bit, wide-bound and zero-bound classes (408 rows more, 1,992 in all). The oracle prints the hexadecimal text of its bounds (`mpfr_ours.h`: `ours_print_hex`); the test requires that the result encloses the oracle's and is at most 1,024 units of the last place wider (12.10.2: valid, should be accurate); ln 2 is computed in integers (series, 1,400 bits, tested against its published digits); the generator refuses operands that are not numbers of the format (above the largest finite value, off the grid of the smallest subnormal). Result: all 408 rows pass, including the threshold rows at 117, 146, 175 and 292 bits, so #569 stays fixed.
- The untimed differential stage of `interval` against MPFR ([#657](https://github.com/Luna-Flow/floating/issues/657) is its first finding): `tools/interval_diff.py` (`gen`, `run`) writes seeded rows of operand intervals for `add`, `sub`, `mul`, `div`, `sqr`, `sqrt` and `fma` in seven classes (ordinary, one unit from the overflow threshold, the subnormal band, far addends, fewer bits than the precision, bounds with more bits than the precision, a zero bound; 1,584 rows at 53, 128 and 512 bits), `tools/interval_mpfr_oracle.c` computes the tightest interval of every row with MPFR directly (directed roundings per bound in the exponent range and with the gradual underflow of `binary`, `tools/mpfr_ours.h`: the mapping of `generate_mpfr_random_oracle.c`, header-only so that other oracle programs share it), and `tooling/src/differential/interval_mpfr` runs the rows on `Interval` and compares both bounds and the operands as the library read them as canonical text (no library reader or writer in the comparison). A second oracle in Python integers must agree with the MPFR one on every row it can compute (1,506 of 1,584; the rest have exponent gaps above 4,000 bits or an undecided `mpfr_sqrt`), a class that does not reach its band (checked from the oracle's flags) is an error, and the rows that differ today are listed with their issue in `tools/interval_diff_known.txt` (a new difference or a listed row that agrees again fails the run). First result: 10 rows differ, all `fma` with the product beyond the range end (#657); the other 1,574 agree. Not wired into `tools/run_ci.py`: the stage needs the MPFR headers on the runner.
- The TestFloat gate (`frontend/testfloat_expr`) judges the operation, not the operation followed by a rounding of the harness ([#438](https://github.com/Luna-Flow/floating/issues/438), oracle audit). The result of a contextual operation, or of `convert_format`, is packed into the bit fields of its format by the front end (a layout written out there: precision, width, bias) and the vector fails with "result not in the format" when the value is not a number of the format; the flags compared are the operation's own, nothing is added by the harness. Before, `BinaryInterchange::from_binary` rounded every result first and OR-ed that rounding's flags in, so an unrounded result or a dropped inexact flag passed. The expected column is compared as text; NaN columns are compared as a quiet NaN result (payload and sign not compared). Tests of the harness itself (`testfloat_expr_wbtest.mbt`): an unrounded result, an unrounded conversion and a result below the smallest subnormal fail, and the packing is checked against bit patterns written out for the four formats. The full binary gate passes on the new harness: 254,280,504 TestFloat vectors, 84 functions, 534 tasks, 0 failures.
- The MPFR random generator rounds a nearest-away result below the smallest normal number on the subnormal grid instead of rewriting the row to ties-to-even ([#438](https://github.com/Luna-Flow/floating/issues/438), oracle audit): nearest-away rows with a subnormal result now exist (53,094 of 2,000,000 rows of the five arithmetic families were affected, 6,316 of them with another value or flags). `tools/check_random_rna_rows.py` is a second oracle for the class (exact arithmetic, no MPFR, no library), run on the committed rows by the Python tests. The 650 committed rows keep their values; 12 are relabelled `n` to `na`; 16 regression rows were added (`reg.rna.subnormal.*`).
- `frontend/itl_expr` reads each decimal and hexadecimal constant of a statement with `Binary::from_string_ctx` and `from_hex_ctx` (nearest, binary64 exponent range) instead of its own reader, which rounded a decimal twice (to `2 * precision + 16` digits, then to `precision` bits): `1 + 2^-53 + 1e-130` now reads as `0x1.0000000000001p0`, it read as `0x1p0`. The `[l,u]` splitting, the default decoration and `[empty]`, `[entire]`, `[nai]` stay in the frontend; a literal the library rejects names itself in the diagnostic at every call site. The interval gate counts do not move (22,892 passed, 14 refined).
- `tools/check_limbs_tier.py` also checks the `enabled=` field of the `luna_limbs:` line: the portable state must report `enabled=false`, the `c` and default states `enabled=true`, and a line without the field is an error. [#544](https://github.com/Luna-Flow/floating/issues/544)
- External baseline, the criterion as a table with two bounds ([#438](https://github.com/Luna-Flow/floating/issues/438), section 8): `CRITERIA` in `tools/external_baseline.py` gives every configuration a `target_ratio` and a `limit_ratio` (`native` and `native-portable` 3 and 3; `wasm` and `js` 5 and 10). The status of a case is `met` (upper end of the net-ratio interval at most the target), `tolerated` (above the target, at most the limit), `not_met` or `unresolved`, and `not_applicable` for a row that judges nothing; a case is borderline when the interval contains either bound. The summary records `limit_ratio` (a summary without it reads the limit as the target), the page counts met, tolerated and not met per runtime and names both bounds. The ratio to `native-portable` stays a diagnostic with no verdict. `wasm-gc` stays unmeasured (the driver links `moonbitlang/async`, which has no wasm-gc runtime).
- Section 6 of [#438](https://github.com/Luna-Flow/floating/issues/438), step 3: the `mpfr_expr` row parser takes the legality of a binary exponent range and precision from `BinaryContext::try_new` instead of its own `e_max < 1` test; the row column `e_min` must still equal `1 - e_max` (the constructor derives it). The parser test also rejects `e_min != 1 - e_max`, `e_max = 0` and a precision above the limit. The `decimal` rows already used `DecimalContext::try_new`; `decimal_gda_expr` keeps its `invalid_context_reason`, which names the GDA rules the constructor does not have.
- `just bench external table OLD NEW...` ([#438](https://github.com/Luna-Flow/floating/issues/438), section 8): a table of one or more new summaries beside an old one (schema v1 or v2), one section per configuration, as Markdown and CSV. Per case: reference and floating time, the ratio of the old summary (marked raw), the net ratio of the new one with its 95% interval, the recorded verdict, the quotient new over old and the like-for-like quotient of the raw ratios (`new_raw_ratio`, `old_raw_ratio`, `quotient_raw` in the CSV; medians with the floor in both times, empty when either is missing); sorted by package, precision and operation; a line of counts per configuration. A v1 ratio and a v2 net ratio are not the same quantity, so the quotient is indicative for the small cases (stated in the output and the tutorial). Pure functions (`table_section`, `render_table_markdown`, `render_table_csv`), unit-tested on two small fixture summaries.
- Section 6 of [#438](https://github.com/Luna-Flow/floating/issues/438), step 2: the corpus is checked, not only generated well. `tools/check_corpus_contexts.py` (quick-gate stage `CONTEXTS: corpus`, well under a second) reads every checked-in `binary` and `decimal` row file, every `decTest` file (and the fetched official corpora when present) and the tuple tables of `library/src/decimal/*_rows_wbtest.mbt` (about 58,000 rows) and fails on a context that the standard of its package cannot have, or on a table that moved and no longer matches. The generators that took their contexts from hand-written lists (`exp_range`, `atan2pi_scaled`, `range_boundary_rows`, `generate_hex_ctx_rows`) validate them through `context_rules` when the module is loaded, and `decimal_row_table.format_row` uses the shared check. The white-box helper `pm1_ctx` of `library/src/decimal` (used by the pm1, rcp, pi-inverse, exp-range and atan2pi-scaled tables) no longer ignores the columns `e_min`, `clamp` and `tininess` of the row: a row that is not an IEEE format aborts the test.
- The nightly workflow runs the unit tests of the whole workspace on `js`, `wasm` and `wasm-gc` (`moon test --target T --deny-warn --frozen`, the gate's command; the pull-request gate only type-checks these targets) and, on an arm64 macOS runner, the tests of `internal/binary_kernel` and `binary` on native in the three states of the row primitives (`LUNA_FLOATING_PORTABLE=1`, `LUNA_FLOATING_LIMBS=c`, default), checked by the new `tools/check_limbs_tier.py` (runner architecture, tier of the default state from one line, `EXPECTED_DEFAULT_TIER`, of the workflow). [#544](https://github.com/Luna-Flow/floating/issues/544)
- Section 6 of [#438](https://github.com/Luna-Flow/floating/issues/438), step 1: one definition of a legal context. `tools/context_rules.py` holds the rules of `binary` (IEEE 754-2019 3.3, `e_min = 1 - e_max`, five roundings, no one-sided range), IEEE `decimal` (the same, clamp on, tininess before rounding) and `decimal_gda` (GDA 1.70 page 10), their limits, one frozen dataclass per standard that validates on construction, and the parser of `testdata/context_vectors.txt` (69 boundary contexts with their verdict). `corpus_common.check_ieee_decimal_context` and `generate_libmpdec_random.legal_exponent_range` now delegate to it. The Python rules and the library constructors are tested against the same vectors (`tools/context_rules_test.py`, `tooling/src/consistency/context_vectors_wbtest.mbt`, native only).
- External baseline on the other runtimes ([#438](https://github.com/Luna-Flow/floating/issues/438), section 8): `bench/external` builds and runs its driver on wasm (under `moonrun`) and js (under node) as well as native (`wasm-gc` stays excluded: the module initialiser of the `moonbitlang/async` dependency is rejected by the runtime at validation); `external_baseline.py run --target native|wasm|js` builds and runs the floating side for that target (the reference side stays the native C process) and records `target`, the runtime versions (`meta.runtime`) and `criterion_applies` (true for the native target only), with `native` as the default configuration of the native target and the target's name otherwise (`native-portable` is named with `--configuration`); where the criterion does not apply the status of every case is `not_applicable`, the tables report ratios and no verdict, and the page never prints `met`. The bootstrap seed now includes the configuration (`derive_seed`), `external_stats.ratio_between` gives the interval of the ratio of two configurations, `publish` and `page` add the ratio of a runtime to `native-portable` (from the two samples files of the release, same operand file and protocol required), a warm flag `w` reports a first-third against last-third difference of the net time, `warmup` runs the calibration experiment of the design page, and `run --warmup-us` overrides the warm-up. In the summary protocol block the target of 3 is `target_ratio` and `target` is the `moon` target. `quick --target` (the ratio flagged above) is now `quick --flag-above`, and `--target` selects the runtime there too.
- External baseline, step 3 of the net-ratio method ([#438](https://github.com/Luna-Flow/floating/issues/438), section 8): the ratio the 3x target is judged on is the ratio of net times, each the median of the differences of case and null blocks, with a 95% bootstrap interval of the ratio from independent resampling of the two sides; a case meets the target when the upper end is at most 3, and is reported as unresolved (judged on the raw ratio, never counted as met) when the reference net is not above zero, the floating net is not above zero, or the interval is wider than 1.25. The summary schema is `external-baseline-v2`: per side the raw, null and net times, per case the raw and net ratios, the status, the drift and order flags, and the method parameters and the `floating_configuration` in `protocol`; the overhead cases and `overhead_floating_ns_per_pass_op` are gone (the 0.10.2 and 0.11.0 summaries stay schema v1). `publish` writes `summary-<version>-<configuration>.json`, `samples-<version>-<configuration>.json.gz` (the pairs; `recompute` recomputes a summary from them) and `summary-<configuration>.md`, and regenerates the tables of that configuration on the performance page; `run` takes `--configuration` and `--moon-env`; `compare` compares net ratios of two resolved v2 cases and raw ratios otherwise; `page` and `recompute` are new. The null operation of the C harness and the `null` case of `bench/external` are removed.
- External baseline harness, step 2 of the net-ratio method ([#438](https://github.com/Luna-Flow/floating/issues/438), section 8): every case is timed as pairs of blocks, a case block and a null block (the same loop without the library call), on both sides. `bench/external` runs a second implementation `null` next to `floating` (Maremark interleaves the blocks); `tools/external_baseline.c` times `pass_null` interleaved with `pass`, each with its own calibrated batch, and writes `variant` and `null_first` on every line. The runner collects the pairs next to the raw samples; the summary and the tables are unchanged until the next step.
- `frontend/gda_expr` reports an exponent range outside GDA 1.70 page 10 as a diagnostic row (invalid context); the frontend tests and the random-differential fixtures of `decimal_gda` use legal ranges (`tools/generate_libmpdec_random.py` validates every context it emits, and the fixture and regression rows were regenerated and rechecked against libmpdec).
- `frontend/gda_expr` and the consistency tests call the GDA functions of `decimal_gda` only (the status-free engine is private there, [#438](https://github.com/Luna-Flow/floating/issues/438)); the corpus counts of the `decimal_gda` gate are unchanged.
- `tools/generate_decimal_gda_plain_rows.py` writes the rows of the plain operators of `decimal_gda` (`+ - * / sqrt`) from Python `decimal` (libmpdec) in the working context of the operators, with no model of this library's algorithm; the white-box test of the rows replaces two tests that compared the operators with the free functions they call ([#438](https://github.com/Luna-Flow/floating/issues/438), oracle audit).
- `tools/generate_decimal_ieee_ops_rows.py` no longer writes the `next_toward` family (510 of 7,479 rows), because `decimal` no longer has `next_toward_ctx` ([#438](https://github.com/Luna-Flow/floating/issues/438)); the rows per operation are a constant (500), so the other rows of the table are the same as before (checked: the new table is the old one without the family). The three consistency tests of `decimal` `next_toward` against decTest representatives are removed with the function; `decimal_gda` keeps `next_toward` and its decTest corpus.
- `tools/generate_libmpdec_random.py` no longer writes a value that a model of this library produces: the class `integer-power-accuracy` (expected value from a Python copy of the decNumber integer-power algorithm that the library also implements) is dropped, `evaluate` returns None for such a case and `format_case` writes no row (the ids of other cases are unchanged). The remaining named classes state their real source in the module docstring and in the `-- expected-difference` comment (exactly rounded value by exact arithmetic; correctly rounded value recomputed at higher precision by libmpdec; the Underflow and Subnormal conditions of GDA 1.70), and `MATH_LIMIT` says where it comes from and that the oracle keeps its own copy. The committed `libmpdec-random.decTest` has no row of the dropped class (650 rows, as before); only the comment line of its one `power-of-ten #351` row changed.
- `tools/code_fingerprint.py` (step 1 of incremental verification, not yet used by a gate): splits the generated C of the native backend into named definitions, normalises compiler counters, locals and object-header layout indices, and fingerprints the code reachable from an entry; the toolchain part of a key; 36 unit tests. Measured on main 044e07dd: 6,381 names, residue 3,420 bytes, every line accounted for; for the PR 672 change exactly 1 definition differs.
- The TestFloat frontend has one function per operation (`arm_add`, `arm_to_uint`, ...) called by the three dispatchers, and each arm records its own name when it runs; the summaries of `--json` of the TestFloat and MPFR frontends have a new field `frontend` (the frontend whose `run` produced them) and the TestFloat one a field `arms` (the set of arms that ran, in order of first use). Incremental verification keys a TestFloat task by the frame plus the arms recorded here. Behaviour of the vectors is unchanged (the smoke and the quick gate pass); `RunSummary::arms` is new public API of the module.
- Incremental verification of the binary gate (`tools/incremental.py`, `python3 tools/conformance.py run --backend binary --incremental`, options `--sample-rate`, `--sample-seed`, `--ledger`): a TestFloat task or MPFR file whose key (code reachable from the frontend entry with the start-up code, the arms recorded by the run, the input, the toolchain) is in the ledger is reported as reused with the commit it ran on and not executed; a random 2 % of them (at least one) are executed and compared, and a difference is a defect of the system (exit status 70). The run is bound to the build (`conformance_cli.build_backend` writes `<exe>.build.json` with the hashes of the executable and of the C file; a mismatch disables incremental), checks which frontend each process ran, and any error while forming keys ends in `incremental disabled: <reason>` with everything run and nothing recorded. Off by default; `run_ci.py` does not use it yet.
- `just verify <scope>` (`tools/verify.py`): the gate of a scope with incremental verification, binary today. `tools/verify_mutation.py` is the mutation test of the system (edits to the kernel, `binary`, `interval`, both decimal packages, the TestFloat frontend and an initialiser, the binding of the build record; a unit that fails on the mutated build must never be reused, which is the check that shares no code with the keys) and `tools/verify_replay.py` replays the keys over the last merged commits of main. An interpreter crash is a failed unit in an incremental run.
- `tools/code_fingerprint.py` normalises three more families of compiler counters: the counter before a generic suffix (`...nextN6constrS1771GcE`, `sort__3S4066GsE`), the counter of a `|` closure (`finalize|25726`, written `_7c25726`) and the numbered labels of source loops (`_2awhile_3024`, `_2afor_4513`). Before, two builds of the same code for which the compiler had numbered a core generic instance differently gave different keys for every unit whose frame reaches it (5 of the last 30 commits of main would have rerun all 538 binary units for that reason alone). Measured: the pair 5d9b2b74 and its parent has 0 changed definitions in the TestFloat frame (9 before); the pairs 671 and 672 give 0 and exactly 1 changed definitions as before. `tools/verify_replay.py` classifies a change by cause per frontend (`frame` of the TestFloat frontend, `start-up`, `mpfr`, `arm`, `none`).
- Incremental verification of the kernel test stages (`tools/kernel_units.py`, used by `just verify binary`; `--full-kernel` runs them in full): the seven kernel stages (product routes and oracles under three states, the oracle tables; 221.5 s measured on 2026-11-21) are units keyed by the content of `library/src/internal/binary_kernel`, the command, the build commands of `moon test --dry-run`, the toolchain and the verifier; the leaf property of the package (it imports only `moonbitlang/core`) is checked from its `moon.pkg`. A reused stage is printed as reused with the commit it ran on; each reusable stage is rerun with probability 2 % (seed printed), and a sampled stage that fails is a defect of the system (status 70). `python3 tools/verify_mutation.py --kernel` is its mutation test. Also: the counter of a `|` closure in `tools/code_fingerprint.py` is anchored at the end of the name.

## 0.11.0 - 2026-11-20

The first release of the changelog of the tools module: it has the version of the library, so 0.11.0 is the release in which the tools moved out of the library module ([#22](https://github.com/Luna-Flow/floating/issues/22), step A and B7), got their own README, manual standard and changelog, and follow the latest MoonBit toolchain (`moonc` >= 0.10.22).

### Fixed

- The MoonBit toolchain of 2026-11-19 (`moon 0.1.20261119`, `moonc` 0.10.22) reports the import of `moonbitlang/async` in `tooling/src/differential/moon.pkg` as an unused package (error 0029 under `--deny-warn`), which turned CI red for `main` and every pull request from 2026-11-20 06:12 UTC ([#459](https://github.com/Luna-Flow/floating/issues/459)). `async fn main` needs no import any more; the import is removed. The module needs `moonc` ≥ 0.10.22. `supported_targets` (no wasm-gc) stays: the executable compiles for wasm-gc but the module fails to instantiate (`moon run --target wasm-gc`), and the `warnings = "-unused_package"` of the `bench/*` packages is still needed (removing it gives 14 errors on wasm-gc).

### Added

- The package `semantic`, moved from the library module ([#22](https://github.com/Luna-Flow/floating/issues/22), step B7): the exact projection of `BinFloat`, `Decimal` and `BallFloat` values that `consistency` and the documentation examples use as oracle. Its tutorial no longer tells the reader to `moon add Luna-Flow/floating@0.10.2`; its pages say that it belongs to this module.
- The package `consistency` (cross-package laws and API audits of the library: 254 white-box tests, no public items), moved from the library module ([#22](https://github.com/Luna-Flow/floating/issues/22), step B7). The module now depends on `Luna-Flow/luna-generic`, which the tests import. The manual pages (API, tutorial, design) are unchanged apart from the module name.
- The binary TestFloat gate (`tools/run_binfloat_interpreter.py`) and the `testfloat_expr` frontend run the format conversions `f16`, `f32`, `f64` and `f128` to every other format (`to_f16`, `to_f32`, `to_f64`, `to_f128`): the operand is read in the format of the function name and the result in the destination format; the narrowing pairs run all five rounding modes and both tininess rules, the widening pairs (exact) one task each. 66 more tasks and 52,632 more level-1 vectors (468 to 534 tasks); four smoke files of twelve rows ([#222](https://github.com/Luna-Flow/floating/issues/222)).

- `tooling/README.md` (the `readme` field of `tooling/moon.mod`) to the standard of the library's README: what the module is, how it is built, a quick start, the package table, the documentation and the contribution rules ([#22](https://github.com/Luna-Flow/floating/issues/22)).
- The manual pages of every package of this module follow the library's standard, and `tools/doc_quality.py` now checks it: the API page has Purpose, Importing, a heading for every public item and the complete interface; the tutorial has the `I want to` table, Quick start, Everyday tasks, Going further, Common pitfalls, Next steps and, for a package with public items, an example that compiles; the design page has the goal, the mathematical background, the decisions, the invariants, the rejected alternatives and the boundaries. Gaps found by the audit are filled: the tutorials of `cli/dispatch` and `differential/harness`, a Going further section for `bench/external`, headings for `MpfrRandomDocument` and `MpfrDecimalRandomDocument`, and compiled examples for the four `cli/*_expr_cli` runners, `internal/conformance` and `internal/runner_cli`.

### Changed

- The `testfloat_expr` front end builds the TestFloat flag mask from the five accessors of `BinaryFlags`, because `BinaryFlags::to_testfloat_bits` left the library ([#22](https://github.com/Luna-Flow/floating/issues/22)). The mask and every result are unchanged.
- The `testfloat_expr` front end, the `mpfr_expr` front end and the manual pages of the frontends call the renamed `bin_float` methods (`pown_ctx`, `compare_quiet_equal`, `compare_signaling_less` and the other five comparison predicates, [#22](https://github.com/Luna-Flow/floating/issues/22)). Every result is unchanged.
- The tutorials of the packages of this module no longer tell the reader to `moon add Luna-Flow/floating@0.10.2`, which does not contain them: they say that the packages belong to this module (a package of the workspace, or `moon add Luna-Flow/floating-tools@0.11.0` once it is published). The package map of the manual says which module each package belongs to and lists `cli/dispatch` and `differential/harness`.

- The module is versioned with the library: `version` is `0.11.0`, the version of
  `library/moon.mod`, and the manifest imports `Luna-Flow/floating@0.11.0`
  ([#22](https://github.com/Luna-Flow/floating/issues/22)). `tools/check_imports.py`
  fails when the two versions and the imported library version differ. The
  description no longer says that the module is not published.
- The module moved out of the library module ([#22](https://github.com/Luna-Flow/floating/issues/22)):
  `bench`, `cli`, `differential`, `frontend/*`, `numeric_expr`, `doc_examples`,
  `internal/conformance` and `internal/runner_cli` are packages of
  `Luna-Flow/floating-tools` and no longer of `Luna-Flow/floating`; their import
  paths are `Luna-Flow/floating-tools/<package>`. `cli` and `differential` are
  entry points only; their behaviour is in the new packages `cli/dispatch` and
  `differential/harness`. The history of these changes before this module had a
  changelog is in the changelog of the library.
